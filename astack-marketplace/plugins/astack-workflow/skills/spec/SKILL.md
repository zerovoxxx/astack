# Spec 工作流

为变更创建或更新单一 SPEC 作为唯一事实来源。仓库只维护 SPEC 和 `docs/astack/INDEX.md`，默认不创建旁路评审或复盘文件。

## 核心流程

1. 阅读 `CLAUDE.md`（以及兼容软链 `AGENTS.md`）、`docs/astack/INDEX.md` 以及现有的 `docs/astack/version/Iteration*_SPEC.md`。
2. 从已有最高编号 `Iteration<N>` 中选取下一个迭代编号。
3. 按 `澄清闸门` 判断是否需要先与用户对齐；需要时停在闸门，取得答复后再继续。
4. 创建或更新 `docs/astack/version/Iteration<N>_<PascalSlug>_SPEC.md`，并使用统一的文档信息表。
5. 在 `docs/astack/INDEX.md` 中添加一行状态条目和简短变更日志行；本次迭代的 INDEX 状态必须与 SPEC `文档状态` 一致。
6. 运行本 skill 自带的 SPEC 校验器，修正本次内容产生的错误和警告。
7. 仅当 SPEC 过大、无法直接执行时，才建议使用 `plan`。

## 澄清闸门

写 SPEC 正文之前的唯一用户断点，用来在落笔前对齐需求边界和方案选择，而不是把既成事实交给用户追认。

满足任一条即进入闸门；一条都不满足时跳过，直接写 SPEC：

- 请求没有写清本次不做什么。
- 请求存在多个合理解释，且不同解释会导出不同的验收标准。
- 涉及用户可见行为，但没有写清用户在什么位置看到什么结果。
- 会改变既有接口、数据、文件布局或工作流约定。

进入闸门时一次性输出一张短卡片，只打断用户一次，包含两块：

- 需求层：不超过 5 个待确认项，每项给出推荐答案和一句理由，让用户只回答有异议的项。
- 方案层：2–3 个候选方案，写清取舍和推荐。需求层尚未收敛时，只给基于明确假设的草案，或声明待需求确认后再出。

只问模型无法从代码库、`CLAUDE.md` 和历史 SPEC 推断出答案，且不同答案会改变目标、非目标或验收标准的问题。技术选型、命名、代码组织和实现细节由模型自行决定，不进入闸门。

闸门最多两轮。第二轮后仍无法确定的事项，写入 `非目标` 或在 SPEC 中明确标注待确认，不继续追问。闸门结论落到 `目标与非目标`、`验收标准`，以及复杂方案时的 `外部参照与设计取舍`，不新增专门章节。

## 自带 SPEC 校验器

创建或更新 SPEC 与 INDEX 后，解析当前 `spec/SKILL.md` 所在目录，并从仓库根目录运行 [scripts/spec-lint.sh](scripts/spec-lint.sh)：

```bash
bash "<spec-skill-dir>/scripts/spec-lint.sh" "docs/astack/version/Iteration<N>_<PascalSlug>_SPEC.md"
```

校验器检查文件命名、文档信息、状态、目标、非目标、验收标准、验证计划、验证记录、变更日志以及 INDEX 引用。出现 `ERROR` 时必须修正并重跑；本次新增或更新内容产生的 `WARN` 也必须修正，既有警告则明确报告。脚本只属于 `spec` 的创建与更新流程，不把它加入 `plan`、`dev` 或 `ship` 的必备步骤。

## 文档信息格式

SPEC 和 PLAN 统一使用同一张 `文档信息` 表。SPEC 的 `关联文档` 写 `无`、前置 SPEC 链接或需求来源；PLAN 的 `关联文档` 写来源 SPEC 链接。`作者` 优先填写当前仓库 `git config user.name` 的结果；为空时写 `AI`。

```markdown
> **文档信息**
>
> | 字段 | 值 |
> |---|---|
> | 文档类型 | SPEC |
> | 文档状态 | 待实施 |
> | 创建日期 | YYYY-MM-DD |
> | 最后更新 | YYYY-MM-DD |
> | 作者 | `<git config user.name>`，为空则 `AI` |
> | 关联文档 | 无 |
> | 一句话目标 | 用一句话描述本迭代要达成的可验证结果。 |
```

## SPEC 状态

全流程只使用 5 个唯一状态词，避免中英混写或自由描述：SPEC 使用 `待实施`、`开发中`、`已完成`、`阻塞`；PLAN 使用 `待执行`、`已完成`。

| 状态 | 含义 | 主要写入者 |
|---|---|---|
| `待实施` | SPEC 已写清目标、边界、验收和验证计划，可以进入 `plan` 或 `dev`。 | `spec` |
| `开发中` | 已开始按 SPEC / PLAN 修改代码或文档，尚未完成最终交付。 | `dev` |
| `已完成` | 最终验证、SPEC / INDEX 更新和交付动作已完成。 | `ship` |
| `阻塞` | 缺少必要信息、外部依赖不可用或连续验证无法推进。 | 任一流程 |

标准流转为：`待实施 -> 开发中 -> 已完成`。`阻塞` 可以从任意状态进入；解除阻塞后回到被阻塞前的状态。

## SPEC 必填章节

每个 SPEC 至少包含：

- 文档信息：使用上方统一表格。
- 目标与非目标。
- 变更范围。
- 实现说明。
- 验证计划。
- 验收标准。
- 验证记录。
- 变更日志。

复杂方案设计必须补充：外部参照与设计取舍。较大变更可继续补充：方案对比、详细设计、实现计划、风险与回退。

## 复杂方案设计

当 SPEC 涉及复杂方案设计时，必须进行 `外部参照与设计取舍` 检查。复杂方案设计包括：

- 影响多个模块、用户流程或长期维护方式。
- 引入新的结构、抽象、依赖或约定。
- 改变既有数据、接口、协议、文件布局或工作流。
- 存在多个可行方案，且方案之间在复杂度、兼容性、扩展性、性能、可靠性或用户体验上有明显取舍。

执行要求：

1. 先理解本仓库现有实现、约束和历史 SPEC，不用外部方案覆盖本项目事实。
2. 参考相同问题域的成熟做法、主流项目、官方文档或通用工程实践；如信息可能过期或用户明确要求行业调研，先联网确认。
3. 在 SPEC 中加入 `外部参照与设计取舍` 章节，简短记录外部参照、可借鉴点、不采用点和本次取舍。
4. 如果判断无需外部参照，必须写明原因，例如：`本次是局部文档/路径修正，不引入新的结构、接口或长期约定。`
5. 不把"行业最佳实践"作为口号；外部参照必须落到设计边界、方案选择、验收标准或验证计划。

## 验证命令解析

编写验证计划时，按以下优先级确定命令：

1. 当前任务匹配的已审批 SPEC / PLAN 中已经确认的具体命令。
2. 项目 `CLAUDE.md` 的“项目质量门”。
3. 仓库已有 wrapper、package script、构建清单或 CI 入口中能够无歧义确认的命令。
4. 仍无法确定时停止，不猜测其他技术生态的默认命令；先指出缺失的项目契约。

只写当前仓库真实存在且适用于本次影响面的命令。命令中的模块、测试目标和路径在执行前必须具体化，不能用另一个项目的工具链作为兜底。

## 验证门槛

每个 SPEC 必须包含至少一条可执行的验证命令。

| 变更类型 | 最低验证要求 |
|---|---|
| Markdown / 文档 / skill | `git diff --check` + 针对性搜索过期引用；项目有更严格门槛时同时执行 |
| 业务逻辑 / 数据转换 | 项目定义的聚焦测试；涉及行为变化时按 TDD 先失败再通过 |
| API / Schema / 跨边界契约 | 聚焦契约或集成测试 + 项目定义的编译、类型检查或构建门 |
| 基础设施 / DB | 项目定义的 repository / migration 验证 + 适用的完整质量门 |
| 用户可见行为 | 在实际呈现层断言渲染值、状态或交互结果 + 适用的项目质量门 |

不得以"人工检查"作为唯一验证方式，除非变更纯属视觉呈现且明确记录了截图或手动步骤。

## 用户可见能力的验收口径

当目标或验收标准声明用户能看到、操作或完成某个流程时：

1. 将数据 / 接口产出与用户可见结果写成独立验收项；前者通过不代表后者已经交付。
2. 写明用户在什么位置执行什么动作、看到什么值或状态，避免只写“输出某字段”“增加某能力”等无法定位呈现层的描述。
3. 验证证据必须与声明处于同一层级。API 或单元测试不能单独证明页面已展示；优先使用页面级、组件级或端到端断言验证实际渲染值、状态或交互结果。纯视觉变化可按项目约定使用带预期对照的截图或明确手动步骤。
4. 新增断言必须能在实现缺失时失败，而不只检查标签、容器或控件存在。高风险行为应通过 TDD 的先失败记录或一次针对性负向校验证明测试有效。
5. 每条用户可见验收项都要能追溯到 `变更范围` 中的实现位置和 `验证计划` 中的证据；任一映射缺失时，SPEC 尚未写完整。

## 边界

- 默认不创建 `BOUNDARIES.md`、`docs/retro/*`、`*_REVIEW.md` 或 `*_CR.md`。
- 不在 `INDEX.md` 中放逐任务细节，细节保留在 SPEC 中。
- 如用户要求临时报告，仅针对该次请求创建，不纳入默认工作流。
