# 合并与 rebase 冲突处理

仅在对齐远端时出现未合并路径后读取。目标是保留双方意图、避免数据丢失，并让验证覆盖真正要落地的集成结果。

## 1. 固定现场

1. 记录操作前的本地 `HEAD`、目标分支 tip、`git status --short --branch`，以及：

   ```bash
   git diff --name-only --diff-filter=U
   ```

2. 逐个处理冲突文件，不批量执行 `git checkout --ours .`、`git checkout --theirs .`、reset 或清理未跟踪文件。
3. 需要理解三方差异时分别查看 stage 1 / 2 / 3：

   ```bash
   git show ":1:path/to/file"  # merge base；add/add 时可能不存在
   git show ":2:path/to/file"  # ours
   git show ":3:path/to/file"  # theirs
   ```

   **rebase 中 ours 通常是目标分支当前结果，theirs 才是正在重放的本地提交。** 不根据名称猜意图，必须结合原提交和 base 判断。

## 2. 冲突分级

### 生成物

- 从仓库脚本、构建清单或 CI 找到权威生成命令，先合并生成输入，再完整重生成输出。
- 不手工拼接生成文件，也不把 lockfile、API client、编译产物等简单选为某一侧。
- 找不到生成器、生成器失败，或连续运行两次后第二次相对第一次仍产生新增变化时停止，不能把不确定生成物标记为已解决。

### 顺序编号资源

- 保留已进入目标分支的编号，本地尚未推送的资源顺延到下一个未占用编号。
- 同步文件名、文件内标识、父链 / 依赖关系、INDEX、SPEC 与仓库内引用。
- 只有项目提供唯一性、单头、链接或图结构机械检查时才自动处理；否则按语义冲突请求用户裁决。

### 源代码、配置与文档语义

1. 分别说明 base → 目标分支和 base → 本地提交各自改变了什么，以及两者是否修改同一业务不变量。
2. 不整文件选择 ours / theirs。只有仓库契约能唯一确定结果、且能用测试同时证明双方行为时，才可合并彼此正交的修改。
3. 以下情况视为需要用户裁决：双方目标互斥，涉及产品口径、安全、数据迁移或兼容策略，delete/modify、rename/rename、二进制冲突，或者无法证明某一侧已被另一侧完整取代。
4. 请求裁决时给出冲突路径、双方意图、可选方案与推荐理由，不把大段冲突标记直接丢给用户。

### INDEX 与清单文件

- 独立新增的条目默认两边都保留；编号撞车时顺延本地条目，不整表选边。
- 删除条目与修改条目相撞属于语义冲突，先确认删除是否有意，再决定保留、迁移或删除。
- 排序、链接和派生清单在内容合并后重新生成或机械整理。

## 3. 继续前验证

1. 确认没有未合并路径和冲突标记：

   ```bash
   test -z "$(git diff --name-only --diff-filter=U)"
   git diff --check
   ```

2. 检查 `git diff` / `git diff --cached`，只暂存已解决的目标文件，不夹带原工作区的其他改动。
3. 为双方原意运行聚焦测试；生成物重跑漂移检查，编号资源重跑唯一性 / 链路检查。
4. rebase / merge 完成后再运行完整项目质量门。冲突前的通过结果不能复用。

## 4. 无法安全继续

- 需要用户裁决或验证无法证明结果时，默认用与当前操作匹配的 `git rebase --abort` 或 `git merge --abort` 中止，确认分支、原 `HEAD` 与工作区变更已恢复，再报告现场；只有用户明确要求保留冲突现场时才暂停在进行中状态。
- 不删除自动 stash 或用户 stash。自动恢复失败时保留 stash，报告其引用与恢复命令，不强行覆盖工作区。
- 同一远端竞态最多重新对齐两轮；持续被推进时停止并报告，不进入无限重试。
