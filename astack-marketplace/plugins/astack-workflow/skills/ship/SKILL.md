# Ship

用新鲜的验证证据、规范的提交信息和安全的 git 操作交付当前变更。

## 授权与流程总览

只执行用户已经授权的交付终点：仅要求最终验证时不提交或推送，仅要求提交时不推送；只有用户明确要求或仓库工作流明确规定时才推送或创建 PR / MR。

当交付包含远端推送时，按以下顺序执行：

1. **预检**：确认变更、分支、操作状态和交付目标。
2. **对齐**：获取远端状态并先把本地工作建立在目标分支最新提交上。
3. **验证**：对对齐后的最终候选内容运行完整质量门。
4. **文档**：完成适用的 SPEC / PLAN / INDEX 状态、SPEC 归档与架构文档同步。
5. **提交**：只暂存本次范围并创建规范提交。
6. **推送**：复查远端竞态；远端有新提交时重新对齐并重验。
7. **报告**：给出证据、提交和交付目标。

## 预检

以下情况停止执行：

- 无未提交变更且无未推送提交。工作区干净但已有本地提交待推送，是合法的 ship 输入。
- 正在进行 merge、rebase 或 cherry-pick。
- 当前处于 detached HEAD 或无法确认当前分支。
- 请求包含远端交付，但无法从上游跟踪、用户指令或仓库约定确认远端与目标分支。

## 先对齐，再做最终验证

仅在本次授权包含远端推送时执行本节。最终验证应覆盖将要落到目标分支的集成结果，而不是尚未包含远端最新提交的旧基线。

1. 当前分支有上游跟踪时，以其远端分支为交付目标；否则使用用户明确指定或仓库工作流唯一确定的目标。仍有歧义时停止，不猜测。
2. `git fetch` 后比较目标分支与 `HEAD` 的领先 / 落后关系；落后时先用仓库约定的安全方式合入远端最新提交，再进入最终验证。
3. 只允许 rebase 尚未推送的本地提交，绝不改写已发布历史。工作区有未提交内容时，不得用 reset、checkout 等方式丢弃变更；使用可恢复的非交互同步方式，并在恢复后检查 `git status` 与 diff。无法确认安全时停止。
4. 对齐或冲突处理改变文件、提交基线或生成物后，重新检查范围并运行完整质量门。

## 项目质量门

按以下优先级确定最终验证命令：

1. 当前变更匹配的 SPEC / PLAN 中已经确认的具体命令。
2. 项目 `CLAUDE.md` 的“项目质量门”。
3. 仓库已有 wrapper、package script、构建清单或 CI 入口中能够无歧义确认的命令。
4. 仍无法确定时停止并报告缺失项，不猜测其他技术生态的默认命令。

最终质量门必须是非修改型命令，例如 check、dry-run、test、build 或 verify。格式化和自动修复属于 `dev` 阶段；`ship` 不运行会主动改写文件的 format / fix 命令。如果不可避免地产生了文件变化，先检查 diff、确认变化属于本次范围，再从最后一次改动后重新运行完整门。

**必须解决本次改动引入的新问题**，已有问题需明确区分。纯文档/skill 变更至少运行 `git diff --check` 和针对性过期引用搜索；项目契约或 SPEC 有更严格要求时同时执行。

## 验证

在最后一次代码或文档改动后，运行新鲜验证。优先顺序：

- 如存在匹配的 SPEC / PLAN，运行其中覆盖本次变更的命令。
- 运行项目质量门中适用于受影响模块的静态检查、编译或聚焦测试。
- 运行 SPEC 或项目质量门要求的完整回归 / 构建验证。
- 纯文档/skill 变更至少运行 `git diff --check` 和针对性过期引用搜索。

存在匹配 SPEC 时，将命令、退出码、日期和覆盖范围记录到 SPEC `验证记录`。

完成前逐条核对验收标准或直接请求成功标准是否同时具备实际改动和同层级证据。用户可见行为必须由实际呈现层的值、状态或交互断言支撑，不能只用数据层或 API 结果代替。

## SPEC 与 INDEX 流程

验证 PASS 后：

1. 将变更文件与相关 `docs/astack/version/Iteration*_SPEC.md` 匹配。
2. 将匹配的 SPEC `文档状态` 设为 `已完成`，并更新 `文档信息` 表的 `最后更新` 日期。
3. 更新对应 `docs/astack/INDEX.md` 的状态为 `已完成`。
4. 如本次变更对应 PLAN，将 PLAN `文档状态` 确认为 `已完成`。

直接请求模式没有匹配 SPEC / PLAN 时，不创建这些文档，并在输出中说明状态更新不适用。状态或文档同步产生新改动后，至少重跑适用的文档检查；若改动了验证契约或可执行内容，则重跑受影响的完整质量门。

默认不创建评审或复盘旁路文件。

## SPEC 归档

仓库存在 `docs/astack/INDEX.md` 和 `docs/astack/version/` 时，在状态同步之后、暂存之前执行归档：

1. 项目 `CLAUDE.md` 或当前 SPEC 已声明归档命令时，优先使用项目命令。
2. 否则解析当前 `ship/SKILL.md` 所在目录，先 dry-run、确认计划后再运行本 skill 自带脚本：

   ```bash
   python3 "<ship-skill-dir>/scripts/archive_specs.py" --root "<repository-root>" --dry-run
   python3 "<ship-skill-dir>/scripts/archive_specs.py" --root "<repository-root>"
   ```

内置归档器仅在根级 SPEC 数量超过 10 时触发，只移动主 INDEX 标记为 `已完成` 的条目，并按物理 `Iteration<N>` 保留最新 3 个已完成 SPEC。它使用 `git mv` 移入 `version/archive/`，同步主 INDEX 与归档 INDEX，兼容“文件名作为链接文本”和“`SPEC` 作为链接文本”两种形态，并在目标碰撞或写入失败时停止、回滚，绝不归档未完成 SPEC。

`--force` 只在用户明确要求或项目规则明确规定时使用。脚本缺失、`python3` 不可用、INDEX 结构无法识别或执行失败时，不手工完成半套移动；停止并报告阻塞。

归档改变文件位置后，检查 `git diff --name-status`，逐个搜索已移动文件名并修正 INDEX 之外的相对链接；项目有 Markdown link checker 时运行它，随后至少重跑针对性引用搜索和 `git diff --check`。归档 no-op 或实际移动数量都写入最终报告。

### 顺序编号资源冲突

若远端新增内容占用了本地尚未推送的顺序编号，只在仓库规则能机械确定下一可用编号和全部引用时自动顺延本地资源：

- SPEC 的 `Iteration<N>` 冲突时保留远端编号，将本地 SPEC 改为下一未占用编号，并同步文件名、标题、INDEX 和仓库内引用。
- migration、发布序号等其他资源按项目声明的唯一性与链路校验处理；项目没有明确规则时不得类推或猜测。

顺延后运行针对重复编号、断链和过期引用的机械检查，并重新执行受影响验证。

## 分支策略

默认不切分支。无论当前分支是 `main` / `master` 还是开发分支，`ship` 都在当前分支完成本次已授权的验证、提交或推送。

只有用户明确要求“切分支”、“新建分支”或“开 PR 分支”时，才创建或切换分支。若用户给出分支名，使用用户给定名称；若用户明确要求切分支但未给名称，再按以下格式命名：

| 类型 | 格式 | 示例 |
|------|------|------|
| 新功能 | `feat/描述` | `feat/add-sector-ranking` |
| 修复 | `fix/描述` | `fix/order-race-condition` |
| 重构 | `refactor/描述` | `refactor/market-service` |
| 文档 | `docs/描述` | `docs/update-api-spec` |
| 构建/工具 | `chore/描述` | `chore/upgrade-dependencies` |

## 提交信息规范

遵循 Conventional Commits 1.0.0，Header 必填，Body 推荐，Footer 按需。

```text
<type>(<scope>): <subject>

[Body: 说明为什么这样改、解决思路]

[Footer: BREAKING CHANGE 或 Closes #issue]
```

**Type**：`feat` / `fix` / `docs` / `style` / `refactor` / `perf` / `test` / `build` / `ci` / `chore` / `revert`

**Subject**：中文，祈使句（"新增"而非"增加了"），不加句号，≤50 字符。

示例：
```text
feat(market): 新增板块优先级评分与轮动分析

引入 P1-P5 评分体系，对标参考项目板块分类映射，
数据通过行业 ETF 日行情异步计算写入 sector_score 表。
```

## 文档同步

检查 `docs/`，若本次变更涉及架构、接口或数据模型，必须同步更新对应文档后再提交。

## Git 安全

### 冲突分级

实际出现未合并路径时，先完整阅读 [合并与 rebase 冲突处理](references/merge-conflicts.md)，记录冲突集合并逐文件处理：

- **生成物冲突**：合并权威输入后完整重生成，不手工拼接或简单选边；找不到确定生成流程时停止。
- **顺序编号资源冲突**：仅按上节和项目现有机械契约顺延本地未推送资源，不整份 INDEX 或迁移目录选边。
- **源代码、配置或其他语义冲突**：先比较 base、目标分支与本地提交的意图。只有仓库契约能唯一确定结果且测试能同时证明双方行为时才合并正交改动；其余情况安全中止当前操作并请求用户裁决。

注意 rebase 中 `ours` 通常指目标分支当前结果，`theirs` 才是正在重放的本地提交，禁止仅凭名称执行整文件选择。

### 操作顺序

- 只在验证 PASS 后提交。
- 暂存前检查 `git status --short --branch` 和 `git diff --stat`，只暂存目标文件。
- 推送前再次 `git fetch` 并比较目标分支；若远端已推进，回到“先对齐，再做最终验证”。最多重试两轮，仍持续推进或无法安全合并时停止。
- 远端新提交、rebase 或冲突处理一旦改变最终候选内容，必须重新运行完整质量门，不能沿用旧结果。
- 使用普通 `git push` 推送到已确认目标；禁止 `--force` 和 `--force-with-lease`。
- 只在用户要求或仓库工作流要求时创建 PR。
- **不使用 `gh` CLI**；首次推送后命令输出中会有创建 MR 的链接，告知用户点击。

## 输出

报告以下内容：

- 验证命令及结果。
- SPEC / INDEX 更新情况（如有）。
- SPEC 归档结果（移动数量或 no-op）。
- 远端对齐与推送前竞态复查结果（如适用）。
- Commit hash。
- 推送目标或 MR 链接。
