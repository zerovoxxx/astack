参数：`$ARGUMENTS`

解析规则：
- 若参数以 `-n` 开头（如 `-n`、`-n src/services/auth.ts`），进入 **通用审查模式**；`-n` 后的内容为可选的审查范围描述。
- 否则，视整个参数为 Spec 文档路径，进入 **方案审查模式**。

# 模式 A：方案审查模式（默认）

请严格按照技术方案 $ARGUMENTS 对当前实现进行代码审查，按文档中的阶段划分分 Phase 完成。本次只做审查与结论输出，不做任何代码修改（但需更新 Spec 文档状态）。

## 文档状态管理

审查**开始前**，将 Spec 文档中标题下方的文档状态更新为 `CR中`：

```markdown
> **文档状态: CR中**
```

若文档中尚无 `文档状态` 行，在标题（`# 迭代 ... Spec：...`）与 `## 1. 文档信息` 之间插入该行（前后各空一行）。

## 每阶段执行流程

对每个 Phase，按以下三步循环：

1. **学习** — 通读本 Phase 涉及的方案内容及所有源文件，理解预期目标与当前实现；
2. **审查** — 按子任务编号顺序逐一核对，检查实现是否满足方案要求；
3. **复核** — 每个子任务审查后重新阅读相关代码，确认结论准确；Phase 完成后做交叉复核（与上下游模块、调用链、配置、边界行为是否一致）。

## 审查检查项

对每个子任务重点检查：

- **实现完整性**：是否按方案落地，有无缺失、漏改、未覆盖分支；
- **实现一致性**：命名、路径、接口、数据流、调用链是否与方案及相关代码一致；
- **影响范围**：改动是否同步覆盖上下游依赖、兼容逻辑、清理逻辑、配置项和边界场景；
- **风险问题**：是否存在潜在 bug、脏数据、兼容性问题、重复逻辑、遗留旧路径等。

## 阶段审查报告（每个 Phase 完成后输出）

- **审查文件清单**：本阶段实际审查的文件
- **审查结论摘要**：按子任务逐条给出结论（通过 / 部分符合 / 不符合）
- **问题清单**：发现的问题，注明影响范围与严重级别（高 / 中 / 低）
- **关键依据**：结论对应的代码位置或行为依据
- **遗留问题**：需进一步确认或方案未明确的点（无则写"无"）

## 约束

1. **唯一权威源**：技术方案文档 + 项目代码，不引入外部假设。
2. **只读不改代码**：本次任务只做审查与结论输出，不修改任何代码；唯一允许的文档修改是更新 Spec 文档状态为 `CR中`。
3. **最小审查范围**：只审查方案涉及的文件和模块，不扩展到无关代码。
4. **结论必须有据**：审查结论基于实际代码和方案要求，不凭猜测；即使"看起来已实现"，仍需核对上下游，不能只看局部。
5. **小幅偏差如实记录**：命名/路径等微调，以代码实际为准判断是否实现了方案意图，在报告中记录差异。
6. **实质性不一致明确指出**：不自行脑补为"等价实现"，明确说明差异。
7. **方案未明确不做推断**：如影响结论，放入"遗留问题"。
8. **根本性阻塞即停**：核心模块不存在、实现前提不成立等根本冲突，立即停止后续 Phase，先输出阻塞说明。
9. **按阶段顺序执行**：按 Phase 编号顺序推进，不跳跃。
10. **不做过度优化**：不提风格类、重构类、可做可不做的建议；只提出有明确依据的真实问题。

# 模式 B：通用审查模式（`-n`）

不依赖技术方案文档，直接对代码变更进行质量审查。只做审查与结论输出，不修改任何代码。

## 审查范围确定

按优先级选取审查范围：
1. 若 `-n` 后指定了文件/目录路径，审查指定范围；
2. 否则，运行 `git diff --name-only HEAD` 和 `git diff --cached --name-only` 获取当前所有已修改/已暂存文件作为审查范围；
3. 若无任何变更，提示用户并结束。

## 执行流程

1. **收集** — 读取审查范围内所有变更文件的完整内容和 `git diff`；
2. **理解** — 梳理变更意图：新增功能 / bug 修复 / 重构 / 配置调整等；
3. **审查** — 按文件逐一审查（见检查项）；
4. **复核** — 审查完所有文件后，做跨文件交叉复核（调用链、类型一致性、边界行为）。

## 审查检查项

对每个变更文件重点检查：

- **正确性**：逻辑是否正确，有无 off-by-one、空值未处理、异步竞态、资源泄漏等 bug；
- **类型安全**：TypeScript 类型是否准确，有无 `any` 逃逸、类型断言滥用、接口不匹配；
- **边界与异常**：错误路径是否处理、边界输入是否覆盖、异常是否正确传播；
- **影响范围**：改动是否同步更新上下游调用方、类型定义、配置项；有无遗漏的联动修改；
- **安全性**：有无敏感信息硬编码、注入风险、不安全的外部输入处理；
- **性能**：有无明显的性能陷阱（不必要的循环、重复计算、大对象拷贝、缺失 memo 等）；
- **一致性**：命名、模式、风格是否与项目既有代码一致。

## 审查报告

输出以下结构化报告：

### 变更概述
- 涉及文件数 / 新增行数 / 删除行数
- 变更意图一句话总结

### 按文件审查结论
对每个文件给出：
- **文件路径**
- **变更摘要**（一句话）
- **结论**：通过 / 有问题
- **问题列表**（若有）：问题描述、代码位置、严重级别（高 / 中 / 低）

### 问题汇总
按严重级别汇总所有问题，高级别优先。

### 总结
- 整体质量评价（一句话）
- 是否建议合入（是 / 否 / 有条件）

## 约束

1. **只读不改代码**：本次任务只做审查与结论输出，不修改任何代码和文档。
2. **结论必须有据**：每个问题必须指向具体代码位置，不凭印象。
3. **不做过度优化**：不提风格偏好、可做可不做的重构建议；只提出有明确依据的真实问题。
4. **关注实质问题**：优先关注正确性、安全性、边界处理等实质性问题，忽略纯格式差异。
5. **项目上下文感知**：基于 CLAUDE.md / AGENTS.md 中的项目规范判断一致性，而非通用最佳实践。
