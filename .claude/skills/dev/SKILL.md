# 按请求、SPEC 或 PLAN 开发

从明确请求、SPEC 或 PLAN 实现变更，保持最小范围并留下新鲜的验证证据。

## 输入模式

尊重用户明确选择的输入模式；用户未指定时，再按仓库治理约定选择：

- **PLAN 模式**：用户指定或当前变更有明确的 `_PLAN.md` 执行入口。
- **SPEC 模式**：没有执行 PLAN，但存在当前变更对应的已批准 `_SPEC.md`。
- **直接请求模式**：用户明确要求直接开发、跳过 SPEC / PLAN，或项目约定允许从清晰请求直接实施。

用户明确要求不写 SPEC / PLAN 时，不得暗中创建或更新这些文档。若仓库强制要求 SPEC 且用户没有明确覆盖，遵守仓库约定；若输入之间冲突或无法确定当前目标，先停止并说明冲突。

## 核心规则

没有新鲜验证，就不声明完成。任务、阶段、直接请求或 SPEC 在对应命令运行并记录结果之前，均视为未完成。

**业务逻辑强制 TDD**：凡涉及计算逻辑、评分算法、策略规则、数据转换的任务，必须先写测试（此时测试应当失败），再写实现（使测试通过）。跳过这个顺序的代码视为未完成。文档、配置、纯脚手架类变更不受此约束。

## PLAN 模式

当存在 `_PLAN.md` 时：

1. 阅读当前任务及其引用的文件，将来源 SPEC 的 `文档状态` 设为 `开发中`，PLAN 保持 `待执行`。
2. 按顺序执行步骤。
3. 每完成一步立即打勾。
4. 运行该任务的验证命令。
5. 将 PASS / FAIL 证据写入对应 SPEC 的`验证记录`。
6. 所有 PLAN 任务验证 PASS 后，将 PLAN `文档状态` 设为 `已完成`；来源 SPEC 仍保持 `开发中`，直到 `ship`。

验证失败时，停止执行并记录失败命令。只有确认无法继续推进时，才将来源 SPEC 或 PLAN 状态设为 `阻塞`。

## SPEC 模式

直接从 `_SPEC.md` 工作时：

1. 将 SPEC `文档状态` 设为 `开发中`。
2. 阅读相关章节和源文件。
3. 做满足当前目标的最小代码改动。
4. 运行覆盖本次改动的 SPEC `验证计划`命令。
5. 写入验证记录行：

```markdown
| YYYY-MM-DD | `实际命令` | PASS / FAIL | 覆盖范围或失败原因 |
```

验证命令 PASS 后，SPEC 仍保持 `开发中`，直到 `ship` 统一设为 `已完成`。验证失败时，停止执行并记录失败命令。只有确认无法继续推进时，才将 SPEC 状态设为 `阻塞`。

更新状态时同步更新 `文档信息` 表的 `最后更新` 日期。

## 直接请求模式

当进入直接请求模式时：

1. 阅读项目指令、相关源文件和现有测试，明确本次假设、成功标准与影响范围。
2. 在修改前说明将采用的验证命令；命令按下节的项目契约解析。
3. 做满足请求的最小改动；涉及业务逻辑时仍执行先失败、再实现、再通过的 TDD 顺序。
4. 运行覆盖最终文件状态的验证，并在最终报告中记录实际命令、PASS / FAIL 和覆盖范围。

直接请求模式不更新 SPEC、PLAN 或 INDEX。实现中出现会改变目标、授权范围或关键设计的歧义时，停止并询问用户。

## 验收闭环

- 每条验收标准或直接请求成功标准，都必须能映射到实际改动和验证证据；只完成底层产出不能替代未实现的消费端行为。
- “用户能看到 / 能用”的结果必须在实际呈现层验证渲染值、状态或交互结果；API、数据层或单元测试只能证明对应底层契约。
- 跨层契约变更同时检查生产方与消费方，并运行能发现接口漂移的项目质量门。

## 验证命令解析

1. 执行用户明确要求的验证命令，并优先采用 PLAN / SPEC 已写明的具体命令；两者均适用且不冲突时都要执行。
2. 缺失或已过时时，使用项目 `CLAUDE.md` 的“项目质量门”。
3. 再从仓库已有 wrapper、package script、构建清单或 CI 入口确认命令。
4. 仍无法确定时停止并说明缺失项，不用其他技术生态的命令代替。

如果实现过程需要改变验证契约，SPEC 模式先更新 SPEC；直接请求模式先说明替换原因与新命令。格式化或自动修复只允许作用于本次范围；命令产生文件改动后，必须检查 diff，并重新运行覆盖最终文件状态的验证。

## 范围纪律

- 使用项目已有模式。
- 不重构无关代码。
- 不基于意图、视觉检查或旧测试输出声明完成。
- 实现与请求、SPEC 或 PLAN 有偏差时，按当前输入模式先更新权威输入或询问用户，再继续执行。
