# 并行执行与合并策略

全仓扫描时，可将审查工作拆分为多个并行子任务以提升覆盖质量和效率。本文件定义拆分方案和合并协议。

## 适用条件

- **全仓扫描**模式下可使用并行策略
- 需要 Agent 环境支持多实例或 Task 子任务（如 Cursor 的 Task tool）
- 每日增量模式通常变更文件集较小，不需要并行

## 拆分方案

按风险域 Tier 拆分为 3-4 个独立子任务：

| 子任务 | 覆盖范围 | 参考 risk-domains.md |
|--------|----------|---------------------|
| **Task-A** | Tier 1.1 主进程核心 + Tier 1.2 引擎适配层 | §1.1 + §1.2 |
| **Task-B** | Tier 1.3 IM 网关 + Tier 2.4 MCP/定时任务 | §1.3 + §2.4 |
| **Task-C** | Tier 2.1 渲染层服务 + Tier 2.2 大型 UI 组件 | §2.1 + §2.2 |
| **Task-D** | Tier 2.3 OpenClaw 配置/引擎 + Tier 3 低风险域 | §2.3 + §3 |

每个子任务独立执行完整的 Layer 1-5 扫描。

## 子任务 Prompt 模板

分派子任务时，每个子任务的 prompt 应包含：

```
你是 FinClaw 项目的 BUG 审查子任务。

审查范围：[具体的文件/模块列表]
审查深度：完整五层漏斗扫描

必读参考文件：
- .claude/skills/bug-review/SKILL.md — 阅读"五层漏斗扫描"（Layer 1-5 方法论）、"BUG 分级标准"、"置信度标准"、"审查准则"
- .claude/skills/bug-review/reference/bug-patterns.md — Layer 2 使用的检查清单，逐项过检
- .claude/skills/bug-review/reference/report-template.md — 输出格式

执行方法：
- Layer 1：获取模块结构概览，识别值得深看的区域。>500 行的文件先用符号概览或 grep 定位，不要全量读取
- Layer 2：逐项过 bug-patterns.md 中的检查清单
- Layer 3：根据模块所属风险域执行架构专项审查
- Layer 4：对每个疑点回答 5 个归因问题（触发条件/失败路径/难发现原因/影响范围/最小修复点），无法全部回答则降为观察项
- Layer 5：按 report-template.md 格式组织发现

输出要求：
1. 按 report-template.md 的单条 BUG 模板输出每个发现
2. 在末尾输出子任务摘要：扫描文件数、发现数（按等级）、置信度分布
3. 将完整结果返回给调用方（不自行写文件）
```

## 合并协议

所有子任务完成后，执行以下合并步骤：

### 1. 去重

同一 BUG 可能被多个子任务独立发现（跨模块问题）。去重规则：
- **指纹匹配**：同一文件 + 同一函数/代码段 = 同一 BUG
- **根因匹配**：不同文件但根因相同（如"多平台分支遗漏"在 isConnected + isConfigured 同时发现）→ 合并为一条，列出所有表现点
- 保留描述最详尽、证据链最完整的版本

### 2. 共识度评估

被多个子任务独立发现的问题，共识度更高：
- 2+ 子任务发现：置信度至少 Medium
- 3+ 子任务发现：置信度至少 High（除非有明确反证）

### 3. 交叉验证

合并后对所有 P0/P1 发现做快速源码回查：
- 验证代码位置是否准确
- 验证触发条件是否合理
- 降级或移除证据不足的条目

### 4. 统一编号与排序

- 按等级降序（P0→P4）排列
- 同等级内按置信度降序（High→Low）
- 统一分配 BUG-NNN / OBS-NNN 编号

### 5. 写入最终报告

将合并后的结果按 report-template.md 格式写入单一报告文件。在报告文件头的"审查模式"中标注"全仓扫描（并行合并）"，并记录子任务数量。
