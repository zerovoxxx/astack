## 文档状态管理

评审**开始前**，将 Spec 文档中标题下方的文档状态更新为 `评审中`：

```markdown
> **文档状态: 评审中**
```

若文档中尚无 `文档状态` 行，在标题（`# 迭代 ... Spec：...`）与 `## 1. 文档信息` 之间插入该行（前后各空一行）。

## 上下文准备

评审前必须获取：
- 完整 Spec 文档内容
- `AGENTS.md`：项目规范、全局开发原则
- `docs/version/BOUNDARIES.md`：该迭代的低成本边界索引（IC4 评审基准；详细边界仍以 SPEC 为权威）
- `docs/retro/golden-rules.md` 中的**活跃规则**区域：历次评审提炼的正面规则
- `docs/retro/patterns.md` 中的**活跃反模式**区域：历次评审识别的反模式
- 相关前置迭代的 Spec（如"前置依赖"中有引用）
- 方案涉及的现有源文件（通过代码搜索定位）

## 评审流程

### 第 1 步：结构完整性检查

对照以下标准章节，检查是否存在缺失或空洞：

| 必要章节 | 作用 | 缺失影响 |
|---------|------|---------|
| 文档信息（版本/日期/前置依赖） | 版本管理与依赖追溯 | 无法判断时效性和前置条件 |
| 背景与目标 | 说明"为什么做" | 研发无法理解动机，任务拆解缺乏优先级依据 |
| 当前状态 / 问题分析 | 说明"现在有什么问题" | 方案可能解决错误的问题 |
| 非目标 | 明确边界 | 研发容易过度设计或遗漏约束 |
| 方案决策（对比 + 选型） | 说明"为什么选这个方案" | 无法评估方案合理性，后续难以复盘 |
| 详细设计 | 说明"怎么做" | 任务拆解无法落地 |
| 数据模型 / 接口定义 | 跨层契约 | 前后端或模块间集成风险高 |
| 交互流程 / 用户流程 | 说明"用户怎么用" | 开发容易偏离用户预期 |
| 跨层字段传递 | 数据贯通 | 容易出现"UI 可见但能力未打通"缺陷 |
| 验收标准 | 说明"怎么算做完" | 任务完成标准模糊，验收扯皮 |
| 风险与缓解 | 预判风险 | 开发中遇到问题无预案 |
| 变更记录 | 追溯演化 | 多人协作时信息不同步 |

### 第 2 步：方案内部一致性检查

在进入逐 Phase 深度评审之前，先做全文级的一致性扫描，识别方案自身的逻辑矛盾和范围偏移：

| # | 检查项 | 评审要点 |
|---|--------|---------|
| IC1 | 目标→解法覆盖 | "背景与目标"中声明的每个问题/目标，在详细设计中是否都有对应解法？有无"声明了目标但无解法"的缺口？ |
| IC2 | 解法→目标溯源 | 详细设计中的每个 Phase/子任务，是否都能回溯到"背景与目标"中的某个目标？有无"提出了解法但无对应目标"的冗余设计？ |
| IC3 | 非目标边界一致 | 详细设计中是否包含了"非目标"中已明确排除的内容？非目标声明是否与详细设计实际范围自洽？ |
| IC4 | 迭代边界一致 | 方案内容是否与 `BOUNDARIES.md` 摘要及 SPEC 自身边界一致？有无超出或遗漏？ |
| IC5 | 冗余内容检测 | 是否存在与迭代核心目标无直接关联的描述、设计或子任务？是否引入了不必要的复杂度或与目标不相关的改造？ |
| IC6 | 前后表述一致 | 文档前半部分（背景/目标/非目标/方案选型）与后半部分（详细设计/验收标准）的术语、范围、约束是否一致？有无前文说"不做 X"但后文又设计了 X 的矛盾？ |

> 若发现 IC1-IC6 有严重不一致（如核心目标无解法、大量冗余设计），先输出一致性问题摘要，再决定是否继续逐 Phase 评审。

### 第 3 步：按 Phase 逐子任务深度评审

按文档中的阶段划分分 Phase 完成。对每个 Phase，按以下三步循环：

1. **学习** — 通读本 Phase 的方案内容，同时阅读方案涉及的所有现有源文件，理解现状与方案目标之间的差距；
2. **审查** — 按子任务编号顺序逐一评估，从以下三个维度检查；
3. **复核** — 每个子任务审查后回顾方案与代码，确认结论准确；Phase 完成后做交叉复核（子任务之间是否有依赖遗漏、顺序矛盾、接口不匹配）。

#### 维度 A：合理性（Rationality）

| # | 检查项 | 评审要点 |
|---|--------|---------|
| A1 | 问题-方案匹配 | 方案是否直接解决"背景与目标"中的问题？有无过度设计或答非所问？ |
| A2 | 方案对比充分性 | 是否列出至少 2 个方案并做优劣对比？选型理由是否明确？ |
| A3 | 迭代边界遵守 | 是否严格遵守 `BOUNDARIES.md` 摘要及 SPEC 自身边界？有无引入超出范围的功能？ |
| A4 | 复用优先原则 | 是否优先复用现有能力？新增模块/接口是否有必要性论证？ |
| A5 | 非目标合理性 | 非目标是否合理排除了不属于本迭代的内容？排除理由是否充分？ |
| A6 | 前置依赖 | 前置迭代产出物是否被正确引用？有无隐式依赖未声明？ |
| A7 | 目标-解法一致性 | 本 Phase 的子任务是否都服务于文档声明的迭代目标？有无脱离目标的"顺手改造"或范围蔓延？ |
| A8 | 冗余度 | 本 Phase 的设计是否精简聚焦？有无可以删除而不影响迭代目标达成的子任务或设计细节？ |

#### 维度 B：清晰度（Clarity）

| # | 检查项 | 评审要点 |
|---|--------|---------|
| B1 | 术语一致性 | 全文术语是否一致？有无同一概念的不同叫法？ |
| B2 | 接口定义精确性 | 接口参数是否有类型、必填/可选、默认值、边界条件？ |
| B3 | 流程可追踪性 | 数据流/调用流是否从入口到出口完整？有无断点或模糊跳跃？ |
| B4 | 代码示例可理解性 | 伪代码/示例是否语法正确？是否与正文一致？ |
| B5 | 验收标准可操作性 | 每条验收标准能否直接转化为测试用例？有无具体输入、步骤、预期输出？ |
| B6 | 任务可拆解性 | 详细设计是否划分出清晰的模块边界，可直接拆出独立、可并行的任务？ |
| B7 | 任务粒度与依赖 | 子任务拆分是否合理，依赖顺序是否正确，是否有隐含的前置条件未说明？ |

#### 维度 C：可行性（Feasibility）— 必须结合代码验证

| # | 检查项 | 评审要点 |
|---|--------|---------|
| C1 | 代码可达性 | 方案依赖的模块/接口/数据结构是否在现有代码中**实际存在**？改造路径是否可达？ |
| C2 | 改动完备性 | 是否覆盖了所有需要改动的文件和调用链？有无遗漏的上下游、边界场景、兼容逻辑、清理逻辑？ |
| C3 | 命名与路径一致性 | 方案中的命名、路径、接口定义是否与**现有代码实际**一致？ |
| C4 | 向后兼容性 | 改动是否保持向后兼容？破坏性变更有无迁移方案？ |
| C5 | 异常与降级 | 是否覆盖关键异常场景？降级策略是否明确？ |
| C6 | 工程风险 | 是否存在数据迁移风险、并发/时序问题、回滚困难等隐患？ |
| C7 | 安全与可测试性 | 敏感操作有无安全机制？关键接口能否 mock 和测试？ |

#### 维度 D：Harness 实践（Harness Practice）— 涉及 LLM 交互设计的方案必审

> 仅当方案涉及 Prompt 注入、Skill 定义、Agent 行为约束、输出格式规范等 LLM 交互设计时启用本维度。纯工程改动（IPC/UI/存储）可跳过。

本维度的核心判断标准：**好的 Harness 是护栏而非牢笼——划定边界、提供上下文，但在边界内给 LLM 充分的自主空间。** 过度设计的 LLM 约束不仅浪费 Token 预算，更会导致回答刻板、丧失推理灵活性、在边缘场景下表现崩溃。

| # | 检查项 | 评审要点 |
|---|--------|---------|
| D1 | 声明式 vs 命令式 | 方案是否优先描述"期望结果"（What to achieve），而非规定"每一步怎么做"（How to do）？过度命令式的步骤编排会抑制 LLM 的推理和适应能力，导致在未预见场景下机械执行而非智能应变。 |
| D2 | 原生能力信任度 | 方案是否存在"LLM 本来就能做好，但仍额外加约束"的过度防御？例如：LLM 天然擅长总结、格式化、对比分析，若方案为这些能力设计逐条规则，属于过度约束。判断依据：去掉该约束后 LLM 表现是否会显著下降？若不会，则该约束是冗余的。 |
| D3 | 刚性模板 vs 柔性引导 | 方案是否用刚性输出模板（固定段落结构、逐项填空）替代了柔性引导（目标描述 + 示例参考）？刚性模板会导致：①不同场景下回答千篇一律；②模板项无数据时 LLM 被迫编造或输出空占位；③用户体验机械化。柔性引导（如"确保覆盖以下信息点"而非"按以下格式逐条输出"）更适合 LLM。 |
| D4 | Prompt 注入精简度 | 注入 LLM 的指令/约束是否精简聚焦？有无冗余、重复或互相矛盾的规则？过长的规则列表会导致 LLM 注意力分散（lost in the middle），后置规则被忽略的概率显著上升。经验法则：单一关注点的约束不超过 5-7 条核心规则。 |
| D5 | Token 预算与注入膨胀 | 方案新增的 Prompt 注入内容有无 Token 量级评估？是否考虑了与既有注入（bootstrap/skills/context sources）的叠加效应？是否可能因注入膨胀导致用户核心上下文被截断或 LLM 注意力被稀释？ |
| D6 | 效果可验证性 | LLM 行为约束的效果是否可通过采样验证（而非假定注入即生效）？验收标准是否包含多次采样以应对 LLM 输出的随机性？约束失效时是否有可观测的信号（日志/输出缺失项）而非静默退化？ |
| D7 | 约束分层与退出机制 | 约束是否区分了"硬性边界"（如合规拒答、数据来源标注）和"柔性建议"（如信息点覆盖、排版偏好）？是否为 LLM 保留了在信息不足时主动说明缺失（而非强制填充）的退出路径？ |

## 评审原则

1. **以"能否拆出好任务"为锚点**：终极目的是判断"研发能否拆出边界清晰、可独立交付、可并行执行的开发任务"。
2. **目标-解法双向对齐**：方案的每个设计都应溯源到迭代目标，目标的每个诉求都应有对应解法；无法溯源的设计即为冗余，无解法的目标即为缺口。
3. **问题必须伴随建议**：每个 ⚠️ 和 ❌ 必须给出具体修改方向，不做"只批评不建设"的评审。
4. **区分优先级**：P0 = 不修无法拆任务；P1 = 不修增加集成风险；P2 = 修了更好但不影响启动。
5. **尊重既有决策**：方案选型有充分论据的，不因偏好推翻，在选定方案内提建设性建议。
6. **关注跨层贯通**：特别注意数据从 UI → Service → Runner → AI 的完整传递链路。
7. **Harness 护栏而非牢笼**：涉及 LLM 交互的方案，约束应划定边界而非填满空间。具体判断标准——当评审发现以下任一模式时，应标记为过度设计并提出轻量化替代方案：
   - **规则膨胀**：为单一关注点注入超过 7 条规则（注意力稀释拐点）
   - **模板固化**：LLM 输出被固定为逐项填空格式，无法根据场景灵活调整
   - **冗余防御**：约束的是 LLM 原生就能做好的能力（如"回答要有逻辑"），去掉后表现不会下降
   - **退出路径缺失**：约束未考虑信息不可得时的合理退出（如要求"必须包含 X"但 X 可能搜不到）
   - **叠加失控**：新增注入未评估与既有注入的叠加 Token 量级，可能挤压用户核心上下文


### 5b. 归档评审报告

将总评报告保存为 `docs/version/review/{SpecFileName}_REVIEW.md`，其中 `{SpecFileName}` 取自 Spec 文件名去掉 `_SPEC.md` 后缀（如 `Iteration58_Skills_Prompt_Index_Mode_SPEC.md` → `Iteration58_Skills_Prompt_Index_Mode_REVIEW.md`）。若已存在则追加，在文件头加日期分隔线。

### 5c. 治理文档完整性检查

检查被评审的 Spec 是否已注册到治理文档（防止手动创建 Spec 绕过 `/spec` command 导致的遗漏）：

1. **检查 `docs/version/INDEX.md`**：迭代状态总表中是否有该迭代的条目。若缺失，按 `/spec` command 第 2 步格式自动补注册。
2. **检查 `docs/version/BOUNDARIES.md`**：迭代边界规则中是否有该迭代的条目。若缺失，从 Spec 的目标 / 非目标 / 严禁项中提炼一句话边界摘要，按表格格式自动补注册；禁止照搬任务清单或长篇严禁列表。

> 这是对"手动创建 Spec 文件"路径的兜底安全网。通过 `/spec` command 创建的 Spec 已自动注册，此步骤会跳过。

### 5d. 自动知识沉淀

根据评审发现，自动写入以下知识库（**当有新发现时才写，无发现则跳过**）：

**写入 `docs/retro/golden-rules.md`**（活跃规则区域）：
- 将评审中发现的**正面设计模式**提炼为新规则（如果 5 个以上 ✅ 指向同一模式）
- 格式：`RN. {规则标题}：{一句话描述}（来源：迭代 {N}）`

**写入 `docs/retro/patterns.md`**（活跃反模式区域）：
- 将评审中发现的**P0/P1 问题**（尤其是跨迭代重复出现的）提炼为新反模式
- 格式：`PN. {反模式名}：{问题描述}（来源：迭代 {N}）。✅ 应改为：{正确做法}`

> 活跃规则上限 15 条，超出时先将最低频规则移入归档区域。

## 约束

1. **唯一权威源**：技术方案文档 + 项目代码 + AGENTS.md + BOUNDARIES.md，不引入外部假设。
2. **只审不改代码**：本次任务只做评审与结论输出，不修改任何业务代码；允许的文档修改：①更新 Spec 文档状态；②归档评审报告；③补注册治理文档（INDEX.md / BOUNDARIES.md）；④更新知识库。
3. **最小审查范围**：只审查方案涉及的模块和文件，不扩展到无关代码。
4. **结论必须有据**：所有结论必须指向具体的代码位置或现状事实，不凭猜测。
5. **方案未明确不做补全**：不替方案作者脑补实现细节，如影响结论，放入"遗留问题"。
6. **实质性不一致明确指出**：不自行脑补为"等价实现"，明确说明差异。
7. **根本性阻塞即停**：若发现某 Phase 的核心前提不成立（如依赖模块不存在、数据结构根本不兼容），立即停止后续 Phase，先输出阻塞说明。
8. **按阶段顺序执行**：按 Phase 编号顺序推进，不跳跃。
