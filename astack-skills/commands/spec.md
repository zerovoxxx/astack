## 🎯 用户输入

$ARGUMENTS

若用户未提供完整信息，需要交互式收集以下必要字段：
1. **迭代编号**（如 `8`、`7.5`、`2.1`）
2. **迭代标题**（中文，如"文件管理优化"）
3. **英文简称**（用于文件名和分支名，如 `File_Management_Optimization`）
4. **一句话目标描述**
5. **作者**（默认使用 `git config user.name` 的值，用户可覆盖）
6. **前置依赖**（依赖哪些已完成/已规划的迭代，可选）
7. **模板分级**（可选，AI 根据描述自动推断）

### 模板分级

| 级别 | 适用场景 | 目标行数 | 选择信号 |
|------|---------|---------|---------|
| **Micro** | 单文件修复、配置调整、文档更新、小 bug fix | ~40 行 | 描述含"修复/fix/配置/config/调整/移除/清理"且预估 ≤3 个文件 |
| **Standard** | 单模块功能、多文件改动、中等复杂度 | ~120 行 | 默认级别，不符合 Micro 或 Full 条件时选用 |
| **Full** | 跨模块架构重构、多 Phase 交付、涉及 LLM Harness | 300+ 行 | 描述含"架构/重构/多 Phase/跨模块/管线/pipeline"或预估 ≥8 个文件 |

- 用户显式指定级别时直接使用
- 用户未指定时 AI 根据上述信号自动推断，并在汇报中说明推断理由
- 推断不确定时默认 Standard

**【通用型护栏】— 所有迭代必须检查**

| 护栏 | 检查时机 | 来源 |

| 跨层数据传递必须在边界点显式过滤，禁止全量透传 | §6 技术实现 | R5 |

**【选型型护栏】— 涉及外部依赖/数据源选型时检查**

| 护栏 | 检查时机 | 来源 |
|------|---------|------|
| 对比表必含"数据权威性"列（一手官方 API > 二手爬取 > 搜索引擎） | §3 方案对比 | R3, P4 |
| 对比表必含"供应链安全"列（依赖数、历史稳定性、审计记录） | §3 方案对比 | R3, P4 |
| 先查是否有成熟集成（MCP Server、Skill、npm 包），再决定自建 | §3 方案对比 | R3 |

**【LLM Harness 型护栏】— 涉及 Prompt/Skill/Agent 行为设计时检查**

| 护栏 | 检查时机 | 来源 |
|------|---------|------|
| Harness 设边界不替模型推理：声明式原则 > 过程化步骤 | §4 详细设计 | R1, P2 |
| 负向约束 + 高质量范例 > 正向枚举清单 | §4 详细设计 | R2 |
| 描述工具/能力要么给完整调用模板，要么只引用不命名（禁止"半知注入"） | §4 详细设计 | P6 |
| 同一能力的调用语义只在一处定义，其余引用不复述 | §4 详细设计 | R7, P7 |
| 共享协议的 Step 0 应为意图分类（路由门），非 universal action | §4 详细设计 | P8(harness) |
| 文档结构必须反映执行优先级——路由门最前，细则在后 | §4 详细设计 | P9 |
| 每种输出结构只定义一次，禁止正文+附录重复定义 | §4 详细设计 | P1 |
| Prompt 架构决策须查阅行业标准或学术基准做对标验证 | §3 方案决策 | R9 |

> 以上护栏不要求在 Spec 中逐条回应，而是在填充内容时作为隐式检查项。若某条护栏与当前迭代无关，自然跳过。

### 第 3 步：在代码仓库创建开发分支（仅按需执行）

> **默认跳过此步骤。** 仅当用户在输入中明确要求创建分支（如提及"拉分支"、"建分支"、"创建分支"、"create branch"等）时才执行。

**从当前所在分支**创建迭代开发分支。

⚠️ **严格禁止**：在创建分支前执行 `git checkout main`、`git checkout master`、`git switch main` 或切换到任何其他分支。必须就地从当前 HEAD 拉出新分支。

执行流程：
```bash
# 1. 先确认当前分支（仅打印，不切换）
echo "当前分支: $(git branch --show-current)"

# 2. 检查目标分支是否已存在
git branch --list "feat/iteration-{N}-{english_slug}"

# 3. 若不存在，就地创建（不指定 start-point，即基于当前 HEAD）
git checkout -b feat/iteration-{N}-{english_slug}
```

分支命名规范：`feat/iteration-{N}-{english_slug}`
- `{N}` 为迭代编号（如 `8`、`7.5`）
- `{english_slug}` 从英文简称派生，全小写、连字符分隔（如 `file-management-optimization`）
- 示例：`feat/iteration-8-file-management-optimization`

**关键规则**：
- 分支基于**当前 HEAD**（即执行命令时所在的分支）创建，**绝不回退到 main**。
- 若目标分支已存在，跳过创建并提醒用户现有分支名。
- 创建后在汇报中明确注明"基于 `{原分支名}` 创建"。
