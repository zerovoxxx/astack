从技术方案 $ARGUMENTS 生成可执行的开发实施计划。

若用户未指定 Spec 文件，列出 `docs/version/` 下可用 Spec 文件供选择。
若用户指定了迭代编号（如 `9`），自动匹配对应的 `Iteration{N}_*.md` 文件。

## 定位

Plan 是 Spec（设计）与 dev（执行）之间的翻译层：

```
Spec（做什么、为什么）→ Plan（怎么做、改哪里、怎么验）→ dev（照 Plan 逐步执行）
```

Spec 用设计语言描述意图，Plan 用实施语言精确到文件和代码。

## 上下文准备

生成 Plan 前必须获取：
- 完整 Spec 文档内容
- `AGENTS.md`：项目规范、迭代边界
- Spec 中所有涉及的现有源文件（通过代码搜索定位）
- 前置迭代的 Spec（如有依赖）

## 生成流程

### 第 1 步：理解 Spec 并提取改动范围

通读 Spec 全文，结合代码搜索，确定：
1. 需要修改/新建的所有文件
2. 每个文件的改动职责
3. 文件间的依赖顺序

### 第 2 步：构建 File Map

列出所有涉及文件，标注操作类型和职责：

```markdown
| 文件 | 操作 | 职责 |
|------|------|------|
| `src/main/main.ts` | 修改 | 新增 IPC handler |
| `src/main/preload.ts` | 修改 | 暴露 API |
```

### 第 3 步：拆分 Task 和 Step

按**功能模块或层级**拆分 Task，每个 Task 内部拆分 Step。遵循以下规则：

**Task 拆分原则**：
- 按功能层级切分（如：Main Process → Preload/Types → i18n → UI）
- 每个 Task 可独立编译验证
- Task 之间有明确的依赖顺序

**Step 拆分原则**：
- 每个 Step 是一个原子操作（添加导入、修改函数、新增代码块等）
- 使用**语义锚点**定位代码位置（如"在 autoLaunch handler 后面"），不使用行号（行号脆弱，代码变化即失效）
- 给出完整的代码片段，AI 执行时可直接使用

**代码片段规则**：
- 展示改动前后的上下文（锚定位置用）
- 标注是"新增"还是"替换"
- 语义锚点格式：`{文件}` 中 `{锚点描述}`

### 第 4 步：添加验证检查点和复核要点

每个 Task 末尾必须有验证步骤：

```markdown
**验证**：
- [ ] 项目编译通过（如 `npm run build`、`tsc` 等）
- [ ] lint 无新增警告（如 `npm run lint`）
```

涉及 UI 的 Task 额外添加手动验证：

```markdown
**手动验证**：
- [ ] 启动开发服务器（如 `npm run dev`）
- [ ] {具体操作步骤和预期结果}
```

每个 Task 还需列出**复核要点**——执行者完成代码后应重点检查的跨文件一致性：

```markdown
**复核要点**：
- [ ] {文件A} 中新增的接口签名与 {文件B} 中的调用是否匹配
- [ ] 跨层契约一致性（如 API 路由/类型定义/调用方三层是否对齐）
- [ ] i18n 键在所有语言文件中是否都已添加（若适用）
```

复核要点不是重复验证步骤，而是针对本 Task 最容易出错的**跨层/跨文件契约**给出检查提示。

### 第 5 步：生成 Plan 文档

在 `docs/version/` 下创建 Plan 文件。文件名从对应 Spec 文件名派生——将 `_SPEC.md` 替换为 `_PLAN.md`：

```
Spec:  Iteration24_Credit_Three_Pool_Billing_System_SPEC.md
Plan:  Iteration24_Credit_Three_Pool_Billing_System_PLAN.md
```

使用以下模板：

```markdown
# 迭代 {N} 开发计划：{中文标题}

> 基于 Spec v{版本号}，生成日期：{YYYY-MM-DD}

## Spec 来源

[`Iteration{N}_{EnglishTitle}_SPEC.md`](./Iteration{N}_{EnglishTitle}_SPEC.md) v{版本号}

## File Map

| 文件 | 操作 | 职责 |
|------|------|------|
| ... | 新建/修改 | ... |

---

## Task 1: {Task 标题}

**依赖**: 无 / Task N
**涉及文件**: `file1.ts`, `file2.ts`

### Step 1.1: {描述}

**位置**: `{文件}` 中 `{语义锚点}`
**操作**: 新增 / 替换

```typescript
// 代码片段
```

### Step 1.2: {描述}

...

### 验证

- [ ] 项目编译通过
- [ ] {其他验证}

### 复核要点

- [ ] {跨文件一致性检查项}

---

## Task 2: ...

---

## 完成检查清单

- [ ] 所有 Task 的编译验证通过
- [ ] lint 无新增警告
- [ ] 涉及 UI 的改动已手动验证
- [ ] Spec 文档状态更新为 `开发完成`
```

### 第 6 步：确认与汇报

输出：
1. Plan 文件路径
2. Task 总数和预计改动文件数
3. 建议的执行方式（`/dev {Plan文件}` 或按 Task 手动推进）

## 生成原则

1. **忠于 Spec**：Plan 是 Spec 的精确翻译，不引入 Spec 中没有的功能和设计决策。
2. **语义锚点优于行号**：用"在 `autoLaunch` handler 后面"而非"line 1676"，避免代码变化导致 Plan 失效。
3. **代码片段可直接用**：给出的代码不是伪代码，是可以直接粘贴的真实代码（基于读取的源文件）。
4. **Task 粒度适中**：每个 Task 改动 1~3 个文件，太大难以验证，太小增加 commit 噪音。
5. **验证前置**：不是做完所有 Task 再验证，而是每个 Task 都能独立验证通过。
6. **进度可恢复**：checkbox 语法支持中断后从断点继续。

## 约束

1. **不执行代码改动**：本命令只生成 Plan 文档，不修改任何源代码文件。
2. **不执行 git 操作**：不执行 `git add`、`git commit`、`git push` 等任何 git 命令。本命令的唯一产出是 Plan 文档文件。
3. **代码必须实读**：Plan 中引用的代码位置和内容必须基于实际读取的源文件，不凭记忆或猜测。
4. **不做设计决策**：如果 Spec 在某处不够明确，在 Plan 中标注 `⚠️ Spec 待明确: {问题}`，不替 Spec 补全。
5. **不超出 Spec 范围**：只覆盖 Spec 定义的改动范围，不因"顺手"引入额外重构。
