请严格按照 $ARGUMENTS 实施代码变更。

## 输入文档识别

根据输入文件自动识别文档类型：

| 文件名模式 | 类型 | 执行模式 |
|-----------|------|---------|
| `*_PLAN.md` | Plan（开发计划） | **Plan 模式**：按 Task/Step 逐步执行，勾选 checkbox |
| `*_SPEC.md` | Spec（技术方案） | **Spec 模式**：按 Phase/子任务执行（传统模式） |

**优先使用 Plan 模式**。若用户指定了 Spec 文件但存在对应的 `_PLAN.md`，提示用户优先使用 Plan。

---

## Plan 模式（推荐）

当输入为 `_PLAN.md` 文件时，按以下流程执行：

### 执行流程

对每个 Task，按以下四步循环：

1. **读取** — 读取 Task 涉及的所有源文件，确认语义锚点位置正确；
2. **执行** — 按 Step 编号顺序逐一完成代码修改，完成后勾选对应 checkbox（`- [ ]` → `- [x]`）；
3. **验证** — 执行 Task 末尾的验证检查点（编译、lint 等），通过后勾选验证 checkbox；
4. **复核** — 按 Task 的复核要点逐项检查跨文件一致性（接口签名、IPC channel、i18n 键等），通过后勾选复核 checkbox。

### 进度追踪

- 每完成一个 Step，**立即**在 Plan 文档中将 `- [ ]` 更新为 `- [x]`
- 中断后可从最后一个未勾选的 Step 继续
- 验证失败时，在对应 checkbox 后追加 `⚠️ {失败原因}`

### Commit 节奏

按 Plan 中的 Commit 指令执行。若 Plan 未指定，每个 Task 完成并验证通过后提交一次。

## Spec 模式

当输入为 `_SPEC.md` 文件时，按以下流程执行：

### 文档状态管理

开发**开始前**，将 Spec 文档中标题下方的文档状态更新为 `开发中`：

```markdown
> **文档状态: 开发中**
```

若文档中尚无 `文档状态` 行，在标题（`# 迭代 ... Spec：...`）与 `## 1. 文档信息` 之间插入该行（前后各空一行）。

### 执行流程

对每个 Phase，按以下五步循环：

1. **学习** — 通读本 Phase 涉及的所有源文件，理解现状；
2. **输出 File Map** — 列出本 Phase 需要改动的文件清单（文件 → 操作类型 → 改动职责），在阶段报告中呈现，作为后续实施的路线图；
3. **实施** — 按子任务编号顺序逐一完成代码修改；
4. **验证** — 执行项目编译检查，涉及 UI 的改动提示手动验证步骤；
5. **复核 + 回写** — 重新读取修改文件确认正确无遗漏，Phase 完成后做交叉复核（改动与上下游是否一致），然后更新方案文档中对应子任务状态。

### 文档状态同步规则

| 时机 | 状态值 |
|------|--------|
| 子任务完成并复核通过 | 已完成 |
| 子任务已开始未完成 | 进行中 |
| 方案与代码存在根本性冲突 | 阻塞（注明原因） |

- 状态必须随实施进度**逐条同步**，禁止事后批量补写。
- 只更新当前涉及的子任务，不改动无关内容。
- 状态必须**真实反映**代码落地情况，不得提前标记。

## 阶段报告（每个 Task/Phase 完成后输出）

- **File Map**（Spec 模式）：本 Phase 的文件 → 操作 → 职责表格
- **修改文件清单**：新增 / 修改 / 删除的文件列表
- **关键变更摘要**：每个 Step/子任务一句话说明
- **验证结果**：编译/lint 是否通过，UI 手动验证提示
- **进度更新**：已勾选的 checkbox / 已同步的子任务状态
- **遗留问题**：冲突或需关注的点（无则写"无"）

## 约束

1. **唯一权威源**：Plan/Spec 文档 + 项目代码，不引入外部假设。
2. **最小改动原则**：只修改方案涉及的文件和模块，不扩散重构。
3. **小幅偏差自适配**：方案与代码有命名/路径等微调时，以代码实际为准适配方案意图，在阶段报告中记录差异。
4. **根本性矛盾即停**：目标模块不存在、依赖不成立等根本冲突，立即停止并说明，等待确认后再继续。
5. **进度逐条同步**：每完成一个 Step/子任务，必须立即更新文档，禁止事后批量补写。
6. **按顺序执行**：按 Task/Phase 编号顺序推进，不跳跃。
