## 🎯 用户输入

$ARGUMENTS

若用户未指定来源，默认从以下途径提取：
1. 当前对话中的关键洞察
2. 最近 5 个评审报告（`docs/version/review/Iteration*_REVIEW.md`）中尚未沉淀的 P0/P1 问题
3. 最近已完成迭代中反复出现的设计/实现模式

## 📋 执行清单

### 第 1 步：内容收集

根据用户指定的来源（或默认来源），收集待分析内容：

- **从对话提取**：重读当前会话，识别：
  - 多次被验证的设计原则
  - 多次踩到的陷阱或错误
  - 被反复强调的约束或规范
  - 成功解决复杂问题的方法论

- **从评审报告提取**：读取 `docs/version/review/` 下指定的 `Iteration{N}_REVIEW.md`，关注：
  - P0/P1 问题（特别是跨迭代重复出现的）
  - ✅ 结论（特别是多个子任务共同印证的正面模式）
  - 维度 D（Harness）相关的发现

- **从开发记录提取**：分析已完成迭代的 Spec 和实现差异，识别：
  - Spec 设计与最终实现不符的规律性原因
  - 被反复删除或简化的设计（可能说明过度设计倾向）

### 第 2 步：知识提炼与分类

对收集到的内容，按以下标准分类：

**黄金法则**（正面规则，应该做什么）：
- 条件：在至少 2 个不同场景/迭代中被验证有效
- 格式：`RN. {规则标题}：{一句话描述，包含具体场景和判断依据}（来源：迭代 {N}/对话/{日期}）`
- 分类：Spec 设计规则 / 代码实现规则 / LLM Harness 规则

**反模式**（负面规则，不应该做什么）：
- 条件：在至少 1 个迭代中造成了 P0/P1 问题，或在 2 个迭代中反复出现
- 格式：`PN. {反模式名}：{问题描述}（来源：迭代 {N}）。✅ 应改为：{正确做法}`
- 分类：设计类反模式 / 实现类反模式 / LLM Harness 类反模式

### 第 3 步：去重与合并

在写入前检查：
1. 新规则/反模式是否与现有条目实质重复？若重复，增强现有条目而非新增
2. 活跃规则是否超过 15 条？若超出，将最低频（最少被触发）的规则移至归档区
3. 新规则编号是否连续且全局唯一？（在已有最大编号基础上递增）

### 第 4 步：写入知识库

**写入 `docs/retro/golden-rules.md`**：
- 新规则追加到对应分类的活跃规则区域
- 若某分类的括号内仅有"待积累"，先删除再追加

**写入 `docs/retro/patterns.md`**：
- 新反模式追加到对应分类的活跃区域
- 若某分类的括号内仅有"待积累"，先删除再追加

### 第 5 步：汇报

输出：
1. 新增的黄金法则（含编号和分类）
2. 新增的反模式（含编号和分类）
3. 合并/增强的现有条目（若有）
4. 移入归档的条目（若有）
5. 当前活跃规则总数 / 活跃反模式总数

## ⚠️ 注意事项

1. **质量优于数量**：宁可少写，不写低质量条目。规则必须有足够通用性，不是特定迭代的临时约束。
2. **可操作性**：每条规则必须足够具体，读者能判断"当前情况是否符合该规则"。
3. **不做否定之否定**：反模式的"应改为"部分必须是正向的行动建议，不能是"不要 X"。
4. **档案式编号**：编号全局唯一递增，归档后编号不回收，确保引用稳定。
5. **来源追溯**：每条规则/反模式必须标注来源，便于未来验证和追溯上下文。
